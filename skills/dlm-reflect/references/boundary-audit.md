# Boundary Audit

“边界”不是某个技术栈专用概念。它表示: 这轮改动本该停在哪, 以及哪些职责不应被混合。

## 优先检查的 6 类边界

## 先做声明范围对照

在谈“边界”之前, 先把当前任务允许改什么说清楚。

步骤:

1. 列出声明范围来源:
   - Task 目标和非目标
   - `<context_manifest>` 中的源码文件 / 入口文件
   - claim/work item 指向的对象
   - 用户本轮明确允许的编辑范围
2. 列出 `git diff` 里的真实改动文件集
3. 对每个改动做标记:
   - **声明内**: 直接属于当前任务目标
   - **合理支撑**: 为了实现或验证声明目标而必须触及的 glue / 配置 / 测试 / 适配层
   - **可疑越界**: 既不属于声明目标, 也不能明确证明是必要支撑

出现 **可疑越界** 时先查明其与 Frozen 目标、Authorized Scope 和具体风险的关系, 不要先合理化, 也不要仅凭文件不在初始清单就自动判 FAIL。

阻塞性 Finding 必须同时给出: 被违反的 Frozen 验收条件或 SSOT、直接证据/可复现反例/失败观测、对当前结果的实际影响, 以及属于当前 Authorized Scope 的证明。无法满足时记为 Advisory/Deferred; 范围外安全、数据损失或 SSOT 基础失效按 `Baseline invalidation` 上报。

### 1. Task Boundary

问:

- 当前改动是否仍在原始 Subtask / Epic 定义内
- 是否出现了“顺手一起修”的静默扩张
- `git diff` 中是否出现了未在声明范围中的可疑文件

若答案是否定, 先判定是:

- 当前任务未闭合
- 还是已经暴露了新任务

### 2. Module Boundary

问:

- 是否把原本分离的模块逻辑直接串在一起
- 是否为了快而跳过既有入口, 直接写入旁路状态

### 3. Layer Boundary

问:

- 是否跨过了本该稳定的层级接口
- 是否把上层决策压到下层, 或让下层反向依赖上层

### 4. Contract Boundary

问:

- 输入/输出/事件/协议的约定是否被悄悄改变
- 调用方是否需要额外假设才能继续工作

### 5. Ownership Boundary

问:

- 数据、资源、生命周期、缓存、锁、句柄由谁负责
- 当前改动是否让所有权变得含糊

### 6. Shared-Workspace Boundary

问:

- claim/lease、多 worker、共享配置、共享文件时是否污染了他人的工作面
- 当前 patch 是否引入新的共享状态冲突

## 判定建议

- 如果只是当前任务未做完: 继续当前 Subtask
- 如果需要额外独立目标才能闭合: 追加 follow-up task
- 如果任务定义本身已经不适配: 回 `dlm-plan`
- 如果知识层解释不了当前边界现实: 回 `dlm-build`
- 如果 follow-up task 需要跨回合保留: 回 `dlm-plan` 正式建任务, 或至少在当前 Task 执行日志中记录
- 如果当前目标、条件和停止线已满足: 结束当前复核; 不因 Advisory 自动创建或执行下一任务
