# Routing Rules

`dlm-reflect` 的价值不只在于发现问题, 还在于把结果分流到正确的下一步。

## 1. `stop-verified` 或进入 `dlm-sediment`

满足以下条件时，当前工程目标可以直接结束为 `stop-verified`:

- 当前 Frozen/已接受目标已闭合并到达停止线
- 适用验收条件、合同和实质安全边界均通过
- 必需证据与声明类型适配
- Grilling 中所有会改变当前完成决定的关键前提均为 `proven`
- 现有 Blocking Finding 均已解除; 其余为非阻断 Advisory/Deferred

纯行政记录未同步、无消费者的 follow-up signal 或“还能优化”不能阻止 `stop-verified`, 也不能推翻已成立的工程结论。

只有用户明确要求、适用合同要求，或真实加载/发布/决策消费者需要知识与状态同步时，才在相同工程结论下进入 `dlm-sediment`。没有该触发条件时不得仅为证明流程完整而沉淀。

输出:

- `任务判定: ✅ 完成`
- `主路由: stop-verified / sediment`
- `是否允许进入 sediment: no（无消费者） / yes（写明触发条件和消费者）`
- `后续任务持久化: 无 / 已记录 / 已 formalize`

## 2. 继续当前 Subtask

满足以下条件时继续当前 Subtask:

- 任务方向是对的
- 只是仍有未完成项或关键验证缺口
- Grilling 仍存在可由当前任务补证的关键 `unknown`, 或已经出现 `disproven`
- 不需要重拆任务, 也不需要知识层改造

输出:

- `任务判定: 🔄 部分完成`
- 明确写出剩余缺口
- `是否允许进入 sediment: no`

## 3. 追加 Follow-up Task

满足以下条件时可建议追加后续任务:

- 本轮主目标已基本成立
- 但又暴露出一个独立、可拆分、值得单列的新问题
- 该问题不应静默塞回当前任务, 且存在真实消费者、决策用途或具体风险

输出:

- 当前任务判定
- 新任务候选名称或范围（默认 Advisory, 不自动创建或执行）
- `后续任务持久化动作`: 回 `dlm-plan` 正式建任务, 或在当前 Task 执行日志中登记“待规划后续任务”
- `是否允许进入 sediment`: 视当前任务是否已闭合而定

## 4. 回 `dlm-plan`

满足以下条件时回 `dlm-plan`:

- 当前任务定义明显过窄、过宽或切分失真
- 为完成目标必须跨出当前 Task 的原始边界
- 需要重排依赖关系或重新拆子任务

输出:

- `任务判定: ❌ 实现偏移` 或 `🔄 部分完成`
- 明确说明为什么这是规划问题而不是实现问题
- `是否允许进入 sediment: no`

## 5. 回 `dlm-build`

满足以下条件时回 `dlm-build`:

- 知识层、路由、模块划分已无法解释当前实现现实
- 某些模式已经重复出现, 且真实加载/决策消费者需要升级为 L1/L2 或领域规则
- 反思结果揭示了长期结构性知识缺口

输出:

- 需要更新的知识层对象
- 原因和影响范围
- `是否允许进入 sediment`: 当前目标已闭合时可为 `yes`; 知识更新是否后置取决于消费者和合同, 不能反向否定工程状态

## 6. Blocked

满足以下条件时标记 blocked:

- 缺少关键依赖、环境、外部决策或不可替代证据
- 当前无法判断完成性或无法安全推进

输出:

- 阻塞点
- 当前已知事实
- 下一步解除阻塞的最小动作
- `是否允许进入 sediment: no`
